# 响应时间账（首字到底慢在哪，哪些办法已经被数字否掉了）

写于 2026-10-05　·　覆盖第廿~廿三轮（2026-09-29 ~ 2026-10-05）的实测与结论。
本文只记**量出来的事实**和**能拧的旋钮**；每一轮的踩坑过程在 `_overnight/RUNLOG.md`，
架构设计在 `docs/情感预热系统设计.md`（该文 §"三条结论"里的结论 2 已被本文推翻，见下面第 1 条）。

一句话现状：**首字路径上本地那半已经基本归零，剩下的钱全在中转（`relay_ttfb`）
和用户点名要保留的那一次敏感等待（`sensitive_wait`）上。**

## 1. 三条计时线，口径不是一回事（不许混着报）

`GET /api/metrics`（Admin Key）里同时挂着三个数：

| 字段 | 量的是哪一段 | 用途 |
|---|---|---|
| `first_token` | 后端**收到请求 → 第一个字发出去** | 唯一等于用户在界面上那块秒表的数，报成绩只用它 |
| `first_token_relay` | 只量中转（`relay_ttfb`） | 判断"是我们慢还是上游慢" |
| `first_token_stages` | 每一段各自 p50/p95/max/次数 | 分诊用；漏埋点会加不上总账 |

段名（`backend/emotion_state.py:283`，窗口 200 条）：

```
route_prep → lock_wait → local_prep → [sensitive_wait] → retrieval → prompt_build → relay_ttfb → generate
     └──────────────────── 这些加起来对不上 first_token，就是有埋点漏了 ────────────────────┘
```

门禁 `分段计时不自证` 用 AST 扫 `get_metrics`，防止有人拿 `first_token_relay` 冒充端到端首字。
快检一律不真打中转，所以门禁里那些段验的是**结构对不对**（段名齐不齐、有没有自证）；
**绝对值只能真机量**——本文第 2、3 节的数全来自真请求。

## 2. 当前真机分布（新默认下，`tools/bench_latency.py`，两批共 18 句真请求，其中 6 句作废重跑）

| 记忆条数 · 那一句 | 每次首字 | 中位 | 备注 |
|---|---|---|---|
| 0 条 · 普通 | 19.0 / 1.8 / 2.1 | **2.1s** | 第一句是冷启动 |
| 10 条 · 普通 | 50.5 / 1.0 / 0.8 | **1.0s** | 同上 |
| 100 条 · 普通 | 17.4 / 0.9 / 1.6 | **1.6s** | 同上 |
| 10 条 · 30 条长历史 | 16.8s（1 次） | — | 样本不够，只是线索 |
| 10 条 · 敏感（等一次） | 7.1s（1 次） | — | 真回话了，没撞 45 秒上限 |
| 10 条 · 带图 | 4.6s（1 次） | — | 回了颜色名 |

对照：第十九轮同工具同档（那时"关思考"还是个空动作）`100 条·普通` 五次是 27.6/23.8/**26.1**/57.5/8.8。
**量级从"几十秒"进到"一两秒"，但这条差值里有中转时段漂移，不能读成"快了 24 秒"。**

三条必须一起说的保留：
1. **每个后端起来之后的第一句是 17~50 秒**，后面几句才是 0.8~2.1 秒。原因还没查清
   （本地那半已经归零、握手只有 0.22 秒，撑不起这个量级），分诊办法见 §6 第 1 条。
   **别把上面这张表读成"她平时 2 秒开口"：开机第一句不是。**
2. 只有 `普通` 三档满足"每档 ≥3 次样本"，其余三档按门禁口径只能当线索。
3. 关掉思考之后**回复变短**（三句 35/25/45 字，开着想常见 60~140 字）。嫌话短的正解是改
   `DIALOGUE_AGENT_PROMPT` 里那句长度要求，不是把思考开回来。

## 3. 已经被数字证实的（可以做下去）

| 做法 | 证据 | 落在哪 |
|---|---|---|
| **回话不带思考**：`reasoning_effort:"none"` | 裸探测 `probe_first_token.py`：不带参数时中转默认就在先想后说（113~636 字走 `delta.reasoning_content`，用户一个字看不见，首个正文被顶到 2.1~13.4s）；带 `none` 后 reasoning **0 字**、首个正文与首帧同刻。真机配对（`compare_wording.py`，各 3 句交替）非敏感那句**首字 16.6s → 4.4s**，`relay_ttfb` p50 **13.89s → 0.95s** | `MODEL_PROFILES["mimo"]["thinking_off"]`、`CHAT_USE_THINKING` |
| **沙箱答案在关掉思考后仍然对** | `MOZ_CHAT_THINKING=0 tools/sandbox_chat.py`：答对 **6/6**、想不起来 0、答错 0、没回话 0，问回去 2/2/2/2/4/2 秒 | RUNLOG 20.6 |
| **全进程共用一个 httpx 连接池** | 裸 socket 各 6 次：TCP 中位 83ms、TCP+TLS 完整握手**中位 222ms**（187~248）。以前每轮、每个后台任务都新建 `ChatOpenAI` → 每次从零握手，这 0.22 秒一直混在 `relay_ttfb` 里 | `llm_config._shared_http_client()` |
| **检索剪枝（跳过必然 0 分的记忆）** | 配对交替 6 次取中位：1000 条 23.2→**13.3ms**、5000 条（上限档）111.6→**60.6ms**、20000 条 582.4→**339.8ms**，约 1.7~1.8×；结果 `(id, 分数)` 逐条对拍不变 | `_keyword_search_raw` + `_prepare_query` |
| **补整库向量移出本轮 + 失败指数退避** | 以前每过一次冷却就有一轮替整库付一次注定失败的往返；现在后台单飞线程补，**下一轮起语义自动生效**。退避 120→240→480…封顶 30 分钟，成功一次立刻复位 | `_request_backfill_async`、`EmbeddingService._note_failure` |

## 4. 已经被数字否掉 / 证伪的（别再设计进去）

| 想法 | 为什么死了 | 证据 |
|---|---|---|
| **"情感分析本来就已经关了思考，所以关思考没用"** | 旧结论建立在一个从未发出的参数上：`_build_extra_body` 第一行 `if not profile: return None`，而当时生效的模型在 `MODEL_PROFILES` 里查不到 → `extra_body` 恒 `None`。所谓"开/关对照"量的**是同一个 payload** | RUNLOG 20.1；现在 `thinking_param_sent/absent` 两个计数让"没发出去"不可能静默 |
| **给中转加 `enable_thinking:false` / `chat_type:"chat"`** | HTTP **200 收下然后静默忽略**，reasoning 照旧 160/172 字。只有 `reasoning_effort` 认；`thinking:{...}` 直接 **400** | `probe_first_token.py` 会把实际发出的键打出来，就是为了不再跑同 payload 的假对照 |
| **同渠道对冲（主请求 T 秒不出字就再打一枪，先出字的赢）** | 8 对里 6 对有效：**单发中位 3244ms vs 两枪取快 3422ms**，配对里"两枪更快"只占 3/6。这条中转**按 IP/账号排队，不按连接排队**，第二枪排在同一支队伍里，只会多烧一份额度。**功能已整块删除**，`--hedge-ab` 这个量法留在工具里 | RUNLOG 23.1 |
| **跨渠道兜底** | 备用渠道 `https://xxs.l.cd/v1` 同一分钟回 **503 没回话**，而主渠道那一句 8.6 秒。而且换渠道＝换嗓子，"没回话时换个声音回"要用户点头才做 | RUNLOG 23.2 |
| **"慢是我们拼历史拼的"** | 第十六轮已测死：12760 字符历史那一臂**最快**（31.1s，空历史 376.1s）。第二十三轮再补一次：30 条长历史 16.8s，和普通档同量级 | §HANDOFF 7.35 |
| **把查询改写留在首字路径上** | 无收益：改写出来的多路查询在语义服务 401 的情况下只喂关键词一路，而关键词剪枝后单查询 13.3ms。流式路径已从 `queries=` 改回单查询，`_run_memory_retrieval` 不再调 `rewrite_query`（`emotion_graph.py:1077`）。**留下的尾巴**：`rewrite_query` 现在只有一个调用方——那个建好却从没被 invoke 的非流式图（死代码，见 §6 第 4 条） | RUNLOG 20.2 |
| **给 5000 条上限做真倒排索引** | 收益上限 60ms 级，风险是**必须改排序**。明确不做 | HANDOFF §8 |

## 5. 能拧的旋钮（都在进程启动时读，改了要重启后端）

| 环境变量 | 默认 | 作用 | 什么时候拧 |
|---|---|---|---|
| `MOZ_CHAT_THINKING` | **`0`（关）** | 回话那一句带不带思考。`1` = 恢复旧的"先想后说"（更慢、话更长） | 用户嫌话太短/太直时试 `1`，用 `compare_wording.py` 并排看措辞再定 |
| `MOZ_SENSITIVE_WAIT_SECONDS` | `45` | 命中敏感话题时，首字之前**为情感分析那一次往返最多等几秒**。`0` = 完全不等 | 用户明确要求保留；动它之前先看 `emotion.sensitive_wait.payoff_rate` |
| `MOZ_EMBED_FAILURE_COOLDOWN` | `120` | 向量服务失败后的首次退避（秒） | 上游令牌 401 属预期，一般不用拧 |
| `MOZ_EMBED_FAILURE_COOLDOWN_MAX` | `1800` | 退避封顶（越退越长，成功一次复位） | 同上 |
| `MOZ_QUERY_REWRITE_TIMEOUT` | `1.2` | 后台落库那侧查询改写的硬超时 | 见 §7：包在 `with` 里的超时是假的 |
| `MOZ_KEYWORD_INDEX_MAX_DOCS` | `20000` | 关键词派生数据超过这个条数就不缓存（剪枝的内存不无限长） | 记忆量真超上限时 |
| `MOZ_PREWARM_HOURLY_CAP` | `6` | 每小时 L2 预热模型调用次数上限 | 空烧额度时往下拧 |

指标怎么看：
- `emotion.sensitive_wait` → `asked / paid_off / agreed / timeout / failed / payoff_rate`。
  现在只有 2/2 + 一条 7.1s 的样本，**兑现率还不到能下结论的量**。
- `emotion.thinking` → `thinking_param_sent / thinking_param_absent` + `chat_use_thinking`。
  `absent` 在开思考那臂是预期值（mimo 的 `thinking_on` 故意不发，用中转默认）。
- `emotion.prewarm` → `asked / built / hit / dup_skipped`。

## 6. 还开着的三件事（按能不能自己动排序）

1. **每个后端第一句 17~50 秒（可以我自己查，不需要表态）**：真机上起后端、发一句，读
   `first_token_stages` 看 `local_prep` 和 `relay_ttfb` 谁大。若 `relay_ttfb` 大 → 中转对"这个 key
   的第一发"另排队，能考虑启动时打一次空请求预热；若 `local_prep` 大 → 是我们的惰性导入/索引构造。
2. **敏感等待值不值（需要攒样本，不需要改代码）**：`payoff_rate` 掉下去再谈上限。注意
   `emotion_analysis_node` 现在也真的拿到了 `reasoning_effort:"none"`，那一次等待可能自己就变便宜了
   ——看几天中位再说，别先动手。
3. **中转偶尔直接不回话，还需要表态（样本：第十九轮 18 次真请求里 2 次直接失败＝11%；
   第廿三轮 8 对里 3 次没回或 16 秒才回）**：对冲已证伪、备用渠道 503，剩下唯一不"换嗓子"的
   办法是同一请求原样重试一次；换模型/换渠道兜底会改变说话的声音，要用户点头才做。
4. **两处死代码，清理要表态（会删掉一条"看着还在"的能力）**：
   - `build_emotion_graph()`（`emotion_graph.py:542`）在 `server.py:195` 建好、存进
     `_app_state["emotion_graph"]`，**但没有任何地方 invoke 它**——真正跑的是 `run_emotion_workflow_streaming`。
     它是唯一还在调 `rewrite_query` 的地方，也是唯一还在用 `queries=` 多路召回的地方。
   - `rewrite_query` + 它那条模块级长寿命线程池 `_REWRITE_POOL`（`memory_manager.py:631`）
     因此实际上已经没有活的调用方。
   删掉＝"多路查询召回"这条能力从代码里消失（README 原来就是这么写的）。所以先问一句，别自己删。
5. **超长对话没有"第三层记忆"**：`_build_dialogue_messages` 里那段"早期历史折成摘要"的分支
   触发线是 `SUMMARY_TRIGGER_ROUNDS = 30` 轮（`emotion_graph.py:245`），而 `_sanitize_history`
   把送进来的历史截到 30 **条**＝最多 15 轮（`emotion_graph.py:251`）——**永远差一倍，这个分支在
   `/api/chat` 上到不了**。第廿轮我把它当成 121.3s 长历史超时的元凶，是错误归因（已认错）；
   改动本身按结构理由保留（首字路径上不该有同步模型调用），**实测收益明确记 0**。
   真实库里 `conversation_summaries` 也是 0 行。这是产品口径问题（聊很久她还记得多少），
   不是性能问题，动它需要你表态。

## 7. 量法上的四条纪律（本轮踩出来的，写在这里防止复发）

1. **数东西的桩不许把被测的东西换掉**：门禁 `连接池不每轮重握手` 第一版替换了整个
   `_shared_http_client` 去数构造次数——量的是我自己的替身。改成只把 `httpx.Client`
   换成 `CountingClient` 子类、生产函数一个字不动，断言才有效。同族：桩打在
   `get_embeddings_batch` 上会把"冷却判断"一起换掉，要打在**上游客户端**上。
2. **配对交替，不要先后两批**：剪枝和措辞都是"同一台子、开/关交替各 6 次取中位"测的，
   否则会把 CPU 抖动和中转时段漂移当成参数效果。
3. **绝对毫秒阈值在同一台机器上跑批时不稳**：那条"本轮检索花了 241ms > 120ms"红过一次。
   改成桩睡 1 秒、只断言"别超 300ms"——要证的是"不等那一批"，不是"我这台此刻多快"。
4. **别把"改代码"和"跑测量"叠在同一时间段**：第廿三轮有 6 句测到一半赶上我在改对冲，
   全报 `HEDGE_AFTER_SECONDS is not defined`（`bench_latency` 会拷贝后端目录，拷到了中间态）。
   测出来是废的还看不出来。
