## 1. 目标与非目标

**目标**
- G1 用户按下发送后，**第一个字出现的时间与长期记忆量无关**，实测目标 P50 ≤ 4s、P95 ≤ 8s
  （现在的 P50 是 28~50s）。
  **第廿三轮状态：非敏感普通句中位 1.0~2.1s，达标**；但**每个后端起来后的第一句 17~50s**，
  这一条 G1 还没兑现，原因未查（分诊办法在 `响应时间账.md` §6）。
- G2 情绪判断的**质量不退化**：本轮该重话的时候不能说轻佻话。判据是用户口径的"像不像人话"，
  不是标签命中率。
- G3 越聊越省：攒下的情感状态要能复用，不能每轮从零想。
- G4 预热失败/过期**绝不能变成用户可感知的故障**（宁可退回朴素措辞）。

**非目标**
- ~~不追求"让中转变快"（我们控制不了，见结论 2）。~~ 这条随结论 2 一起作废：
  **能控制的是"让它少想一段"**（`reasoning_effort`、连接复用），控制不了的是**排队**
  （对冲、换连接都实测无效）。分界见 `响应时间账.md` §3/§4。
- 不做真倒排索引、不做情感向量化（HANDOFF §8 明确不做）。
- 不把"推断出来的情感对策"当事实写进长期记忆——这条是硬红线，见 §6.4。
- 不承诺当天见效：**这个账号目前长期记忆 0 条**（HANDOFF §6），基线只能是空的；
  P1 之后首字会立刻变快（因为不再等模型），但 G3 的收益要聊几周才显现。

## 3. 设计总览：三层信号，只有一层在首字路径上

```
用户输入
  │
  ├─ L0 即时信号（规则，毫秒，每轮必跑，永不失败）
  │     EmotionAnalyzer 关键词 + 句式（？/！/否定/重复）+ 命中 care_items 的类别
  │     → live = {emotion, intensity, topics[], sensitive[]}
  │
  ├─ L1 情感基线（后台低频生成，落库，读内存）
  │     这个人平时的底色、常见触发主题、雷区、吃哪套安慰
  │     → baseline = {..., revision, updated_at, source_watermark}
  │
  ├─ L2 临时情感对策（触发式预热，后台异步，落库带 TTL，本轮不等待）
  │     L0/关键词命中某个主题（健康/考试/工作/家人/关系/金钱/宠物…）
  │     → 排一个 prewarm 任务：深检索该主题记忆 + 1 次模型调用
  │     → plan = {topic, 该提什么, 别提什么, 语气强度, 追问方向, expires_at, matches}
  │
  └─ 组装本轮措辞上下文（纯内存读取，不调模型）
        ctx = L0 ⊕ (L1 若新鲜) ⊕ (L2 若存在且主题匹配且未过期)
        → 立刻进对话流式生成          ← 首字不再等任何情感模型调用
        后台：把情感模型调用作为"校正器"排队跑，结果写回 L1/L2 与落库标签
```

**读路径的唯一原则：首字路径上不许有任何一次上游往返**（除了生成本身）。
L1/L2 都是"读内存/读库 + 判新鲜度"，读不到就退回 L0，绝不 block。

## 4. L1 情感基线

**内容（JSON，落到新表 `emotion_state`）**

| 字段 | 含义 | 为什么要它 |
|---|---|---|
| `tone_default` / `tone_floor` | 平时语气档位、底线档位 | 空库冷启动也能给出"朴素但不错"的语气 |
| `底色情绪` (baseline_emotion) | 近 30 天最常出现的情绪 | 决定她开口是轻快还是放低声音 |
| `触发主题[]` | 一提就容易有情绪波动的主题（含证据条数） | 决定 L2 要不要预热、优先预热哪个 |
| `雷区[]` | 明确不能拿来打趣/不能主动提的（忌日、病症、失败的考试） | 直接对应昨晚修的"忌日别说快乐" |
| `吃哪套安慰` | 共情型 / 给办法型 / 别问太多型 | 措辞结构，比情绪标签更能影响"像不像人话" |
| `revision`, `updated_at`, `source_watermark`, `confidence` | 新鲜度与可信度 | §6 一致性全靠这几个字段 |

**生成时机（全部在后台，永不在本轮等待）**
- 每轮对话的 `run_save_job` 之后，追加一步"基线刷新检查"（已有队列，不新起线程）；
- 或 `care_loop` 心跳里按水位跑（复用 `graph.sync_all` 的写法）；
- 触发条件：`source_watermark` 落后于（记忆写入 / 档案卡 PUT / 删记忆 / 关心事项变更）
  且距上次生成 ≥ `MOZ_BASELINE_MIN_INTERVAL`（默认 6 小时）——避免为聊天窗口里 3 句话反复重算。
- 冷启动/基线缺失：`baseline = null`，本轮只用 L0；界面上不许出现"我在了解你"这类话术。

**输入只允许来自**：长期记忆正文、档案卡字段、`care_items`（含 kind/repeat）、
`working_memory.summary`、`care_log` 的 ack 结果（用户有没有回话、回了几个字）。
**明确不许来自**：moz 自己上一轮的回答原文（第十四/十五轮刚把"回声当事实"堵住）。

## 5. L2 临时情感对策

**触发条件（L0 之外再省一层：不命中就不排队）**
- L0 的 `topics` 非空，或输入命中 `care_items` 的标题/类别词表（复用 `ITEM_KINDS`），
  或命中 `触发主题[]`；
- 且该主题在 TTL 内没有现成 plan（去重）；
- 且当前小时配额未满（§7 限流）。

**plan 里必须有的东西**：`topic`、`该提`（1~2 条具体事实引用，来自检索结果，带 memory_id）、
`别提`（雷区交集）、`语气强度`、`追问方向`、`expires_at`、`based_on_watermark`。

**TTL 与主题匹配双闸**（这是本设计最容易出事的地方）：
- 过期（默认 30 分钟，敏感主题 5 分钟）→ 不许用；
- 本轮 L0 主题与 plan 主题不一致 → 不许用；
- 只过了一闸也不许"参考着说"，宁可退回 L1。
理由：对策包是"推断"，拿错主题的推断回话，比没有推断更伤人（例：把"复查"的对策用在"体检报告出来"上）。

**本轮不等它**：plan 是为本轮的**下一句**和**下一次同类对话**准备的。
唯一例外是 `sensitive` 命中（如 复诊/忌日/面试当天）——此时首字之前先等那一次情感模型调用，
上限 `MOZ_SENSITIVE_WAIT_SECONDS`（默认 45 秒）。这条已实现并在跑，取舍见 §10 未决 1。

## 6. 一致性与硬约束

1. **落库，不能只放内存**：`--reload` 一改 `.py` 就清进程内状态（HANDOFF §1）。
   L1/L2 都写 `emotion_state` 表；内存里只放一份带 TTL 的镜像。
2. **任何改动记忆/档案/事项的地方都要 bump 水位**，否则基线会带着已经删掉的事实回话
   （§7.1 那个"直接删库界面还是旧的"的坑，同一类）。作废统一走一个函数，不许散落。
3. **`reap()` 语义延伸**：用户删掉的记忆/事项，必须同时让它参与的 plan 立刻失效。
4. **红线：plan/baseline 不得进入 `memories` 表**，不得被 `search_memories` 命中。
   它们存在自己的表、`source_type='derived'`，导出（`/api/export`）里单列一节，用户能看见能清。
5. 敏感类别黑名单：`health`、忌日、`birthday` 已过期的年份、落榜/分手续费等——
   只允许"别提"方向的推断，不允许生成"主动提起"的建议。
6. 界面与文案不许承诺"我已经摸透你的情绪"；能说的只有"聊得多了我会更懂你的说法"。

## 7. 成本与限流

- prewarm 与基线刷新**共用 `SaveWorker` 单飞队列**（`save_queue.py`，已有）：
  一次只跑一个，天然防风暴；不新开线程、不新开循环。
- 硬预算（可配环境变量，默认值）：prewarm 每小时 ≤ 6 次、基线每 6 小时 ≤ 1 次、
  单轮总模型调用（含后台落库四步）≤ 6 次。超了直接跳过——预热是锦上添花。
- 失败静默：任何预热异常只记日志 + 计数，不影响回话；连续失败进 10 分钟冷却
  （照 `EmbeddingService` 那个 401 冷却的写法）。
- 中转被自己打满的坑：selftest 的 `限流不误伤本地` 连发 80 次会占 IP 桶（§7 已挪到最后）；
  预热的配额判断要读同一份桶状态，别再加一条独立计时器。

## 8. 指标与门禁（不达标就不许合并）

**新增只读指标**（`/api/metrics` 里加一节，仿 `get_search_metrics`）：
`ttft_p50/p95`（首个 token 前耗时）、`prewarm_hit_rate`、`plan_expired_used_count`
（**必须恒为 0**）、`derived_leak_count`（plan/baseline 混进 memories 的条数，**必须恒为 0**）、
`baseline_age_seconds`、`live_vs_model_agreement`（L0 与模型标签一致率，用它决定
将来能不能彻底删掉阻塞调用）。

**selftest 新增快检项（一律不调模型，用临时目录 + 临时 db_path）**：
1. `情感三层不挡首字`：把模型客户端打桩成 sleep(5)，断言 stream 首个 token 早于 5s；
2. `过期对策不许用`：造一个 `expires_at` 已过 / 主题不符的 plan，断言回落到 L1；
3. `推断不落进事实`：跑一轮带 prewarm 的落库，断言 `memories` 里没有 `source_type='derived'`；
4. `删记忆要让对策失效`：删掉 plan 引用的记忆 → 水位变、plan 不可用
   （对齐 §7.1 与 `reap()` 的既有语义）；
5. `重启后基线还在`：写库 → 新建实例读回（证明不是只活内存）；
6. `预热配额与冷却`：连打 N+1 次只跑 N 次。

**沙箱端到端**（沿用昨晚改进过的 `sandbox_chat.py`，通过率不再骗人）：
同一组 12 句话，记录改造前后的 `ttft` 分布与人评结论；
人评口径只有两条：**这话像不像人说的**、**这条记忆对不对**。
