## 环境坑（别再踩）

- `.bat` 只能纯 ASCII；含中文的 `.ps1` 必须 UTF-8 **带 BOM**，否则路径静默变坏。
- Git Bash 会吃掉 `/c` 和 `/tmp`；需要时 `MSYS_NO_PATHCONV=1`。
- 控制台打中文要 `PYTHONIOENCODING=utf-8`。
- Qoder 内置浏览器面板没点开时，截图/点击必失败 → 用 `evaluate_script` + `node --check` 代替。
- 后端是 `--reload`：改 .py 会重启，**内存里的当天额度/静默状态会清零**；自测脚本别假设进程连续。
- 中转慢（25~35s）且偶发连接失败：先怀疑网络，再怀疑代码。

| 合计 | 470ms | |

每次都走完一次 401 才降级；三条改写就打三次，而且这个错永远修不好，所以每一轮都在白打。

| 活跃条数 | 关键词阶段（20k 条，单次查询） |
|---|---|
| 老写法 | 598ms（分词 253 + 建 DF 266 + 统计词频 301 + 逐条匹配分 103，重叠计时） |

### 2. 修一：向量服务加失败冷却

`EmbeddingService` 报错以后 120s 内（`MOZ_EMBED_FAILURE_COOLDOWN`）直接回 `None`，不再打网络；
一旦成功就清零。顺带两件：
- 补向量**一批最多 64 条**、按重要性先补最值钱的。原来是一次把整库发出去，5000 条时那就是一个
  5000 条文本的请求，还没降级先把自己卡住。
- 冷却期内连"谁缺向量"的全库遍历都跳过（那条列表推导在 20 万条时也要 90ms）。
- 写路径同样受益：`add_memory` 每条要一次 `get_embedding`（~110ms 的 401），`_resolve_fact_conflicts`
  每次抽取也要一次——现在都直接短路。

语义阶段：**338ms → 0.4ms**。

### 3. 修二：关键词 BM25 按用户缓存语料派生数据

分词、词频、清洗后的正文只跟语料有关、跟查询无关，原来却每次查询全库重算。现在：
- 每个用户缓存一份，一轮 3 条改写共用；
- 写操作只作废**聚合**（DF 表、文档列表要和新集合对齐），每条记忆的派生数据留着接着用——
  正文是不可变字符串，用对象身份 `is` 兜底，所以加一条记忆之后的首次检索只为新记忆分词；
- 查询侧派生数据（2–4 字子串表、词集、分词）提到循环外并加 `lru_cache`，idf 每个查询词只算一次。

**打分公式一个字符都没改**，排序、并列名次的破序规则都和以前一致。

两个踩过的坑（写下来免得再犯）：
1. `_match_score` 改成"自己算一遍查询派生数据"以后，逐条打分的循环反而从 103ms 涨到 578ms（20k 条）——
   任何"每条记忆都要调一次"的函数里都不能有查询侧的重复构造。加 `lru_cache` 才落回 101ms。
2. 不缓存的分支（超过 `MOZ_KEYWORD_INDEX_MAX_DOCS=20000`）如果还照旧往 `derived` 里写，
   等于每次查询白建一个 2 万条的临时字典：20k 那档从 718ms 变 822ms。加分支要顺着
   "这条路径一共分配了什么"再看一遍。

内存代价：派生数据实测 **~4KB/条**（词元字符串占大头），5000 条 ≈ 19MB，很划算；
20 万条要 800MB，所以超过 2 万条**故意不缓存**——那已经不是这个应用会到的地方。

### 1. 先看清原来为什么"孤"

### 2. 图长什么样（新模块 `backend/care_graph.py`）

- **节点**：`item:<事项 id>`（记下的事）和 `memory:<记忆 id>`（记得的事实）。不新造第三种存储。
- **枢纽**：`person:妈妈`、`topic:答辩` 这种标签节点。**只存"节点 → 枢纽"的有向边**，
  "两件事相关"是查询时沿枢纽走两步得到的 → 新记一条事实不需要和全库比一次，边数只跟枢纽数走。
- **同场直连**：一次抽取里前后 5 秒内记下的几件事本来就来自同一句话，额外连一条 `together` 边。
- **打分**：`权重 / (1 + ln(枢纽连着多少条))`，人 > 主题 > 同场；被好几个枢纽同时连上的邻居加成。
  并且 `HUB_DEGREE_CAP=60`：**80 条事项都含"体检"这种词不做桥梁**——什么都能连等于噪声发生器。

抽枢纽**纯规则、不调模型**（这台机器中转随时挂，挂了也不能突然不会关心人）：
称谓词典 + "我妈→妈妈"这类归一 + `老/小/阿 + 字` + `姓 + 总/工/哥/姐…`。
误伤比漏连更贵，所以带停用词和"前一个字是 小/大/阿/老 就不算"的判断：
`小姐姐你好，我小憩了一会儿` → 一个人都不抽；`我妈生日是10月5日` → 妈妈。

### 3. 用在哪儿

`care_engine.collect()` 给每条到点事项附上 `context`（最多 3 行，如
`关于妈妈：用户的妈妈喜欢养花`），`_polish` 的提示词里明确写
"最多挑一条自然地带上，让这句话听像是记得而不是提醒音；用不上就一条都别硬塞"，
带上下文时字数上限从 45 放到 55。**模型挂了照样说模板那句**，关联只是加分项，不会把功能弄哑。

### 4. 边怎么维护（关键：不能把代价摊到每轮对话上）

- 按**水位增量**：`care_graph_state` 记 `item_at/memory_at`，只有改过的事项/记忆才重新抽枢纽。
- 心跳（每 60s）顺带 `sync_all`，所以自动记下的事最慢一分钟就连上线；
  手动在界面加的事项走接口当场就 sync（等一分钟用户会觉得"我明明刚说过"）。
- 幂等：一个节点的所有边整批重写，改措辞不会留老边。

### 5. 三条隐私底线（自测第 26 项 `事件关联成图` 钉住）

1. 用户**软删一条记忆**或删掉一个事项 → `reap()` 按 `memories.data` 里的 status 断边，
   已经抹掉的事不能从图里漏回来当邻居；
2. 「清空一切」→ `care_graph.clear_user()` 一起清，并返回 `links_removed`；
3. 关联只吃"标题/正文本身"，不碰对话原文，也不新存一份事实。

顺带一个坑：`reap()` 中途报错必须 `rollback()`，否则半个写事务留在自己的连接里，
同库其它写入会被 `database is locked` 挡死（自测第一次跑就是这么炸的）。

## 第七轮（19:40–20:20）：事件先后链——让 moz 会问"后来怎么样了"

用户从三个方向里选了"事件之间加先后链"。上一轮的关联是平铺的：知道"这两件事都关于妈妈"，
不知道"答辩在前、出结果在后"，所以只能提醒孤立的一条。

### 1. 三个会静默吃掉链的坑（我自己上一轮写的，先修再建）

- `_replace_edges` 删旧枢纽边用的是 `rel != 'together'` → **心跳每 60 秒把链抹一次**。改成 `NOT IN (together, after)`。
- `_hubs()`/`stats()`/`describe()` 都是"非 together 即枢纽" → 链边的 `item:<id>` 会被当成枢纽，
  `related()` 立刻连出不相干的邻居。三处统一显式排除。
- `emotion_graph.run_emotion_workflow_streaming(...)` 只拿到 `care_store`，拿不到图 →
  **真实对话路径根本建不出链**（链只在抽取时产生）。加 `care_graph` 形参并透传。

第一条被自测的幂等断言钉住，第二条被"链不许污染 related()"钉住，第三条只能靠沙箱端到端——
这就是为什么门禁里必须留一条真跑后端的回测。

### 2. 链怎么存

`care_links` 加两列（`ALTER TABLE` + 捕异常，老库自动跟上）：`offset_days`（-1 = 不是链边）、
`source`（`llm` / `rule`，出问题时一眼分清是谁连错的）。新关系 `after`：
**src 这件事发生在 dst 之后 offset_days 天**（抽取天然得到的是"这件在那件之后"，
叫 `precedes` 每次都要翻转方向，容易写反）。

规矩：**一件事只允许一个前件**（写新边前先删该事项的旧 after 边）——前件不唯一时 moz 会问错话，宁换不叠。
`reap()` 多两条：链两端任一事项被删/被归档就断边。

### 3. 链怎么来

模型路径：`PROMPT` 加 `after`/`after_days` 两个字段，并写明"after 指向**先发生**那件，填反了 moz 就会在答辩当天追问结果，拿不准给 null"。
真模型实测输出（MiMo，temp=0）：
```
项目答辩 due=2026-09-30
答辩出结果 due=2026-10-07  after=项目答辩   after_days=7
决定是否续约 due=2026-10-07  after=答辩出结果 after_days=0
```
规则路径（中转挂了也认）：只认"锚点 + 后 + 数量 + 单位"一个句式，`答辩之后一周出结果`
→ `('答辩', 7天, '出结果')`；天数单位支持 天/周/星期/个月/月/年 和 中文数字/半。

**放弃条件**（任一成立就不建边）：锚点文本空；锚点既不是任何事项标题、也不是唯一一个包含关系的命中；
命中 ≥2 个；算不出天数；两端同一件事；天数越界。`_match_anchor()` 里不做任何模糊评分——
**说错话比不说的话严重**。

顺带修一个老毛病：`_fallback_items` 以前整句只取第一个分句，
"我妈生日是10月5日，我下周三面试"永远只记一条 → 现在按分句扫（上限 3 条，每句仍要独立通过触发词+日期判定）。
另一个：`TemporalExtractor` 解出的时间戳以前被丢回 `due_date=None`，
于是"下周三答辩"是一条**没有日期**的事项——既不会到点提醒，也当不了链的起点。现在真的用上了。

### 4. 链怎么问

`collect()` 在事项循环**之前**算链：`expect = 前件日期 + 间隔`，后件自己有日期时取 `min`（不抢跑）；
`expect <= now <= expect + 36h`（跨安静时段）；后件 `last_fired_at >= expect` 就当已问过。
链候选一旦存在，就把后件从普通事项候选里**抑制掉**——同一件事一天只说一遍，说的那个带上下文的版本。

配额：`MAX_CHAIN_PER_DAY = 1`，一天最多顺一条链；归「到点提醒」开关管，不吃话多话少名额；
`care_log(kind='chain')` 让它照旧受 90 分钟间隔和每日 8 条硬上限约束。链在场时压掉 `open_loop`
（否则 90 分钟后 moz 会换个说法再问同一件事）。

**期望时间只在图里算，绝不回写 `care_items.due_at`** —— 用户看到的日期仍然只有他自己说的那个。

措辞：`why` 一句装下前后两件事，system 里单列一行"这两件事有先后…今天该问的是后者，
只能提这一条链，别把前一件当提醒再念一遍，也别自己编结果"；模型挂了走
`上次说的项目答辩，后来出结果怎么样了？`。

### 5. 门禁

selftest 第 27 项 `事件先后链`（临时目录 + 探针用户，不碰真实库）钉住 8 件事：
规则兜底建得出链、"之后三天"没点名前件就不许连、重复说不幂等就报错、
到期只以 chain 身份问一次、问过了就安静、一天不超过一条链、到硬上限就不发、
提示词里同时有前后两件事、删父件断链、链不污染 `related()`、不传 graph 时行为与改动前一致。

顺手补了门禁的一处盲区：`backend/tests/`（122 条 pytest）一直不在我的三条门禁里，
这轮跑它才发现一条断言早在几轮的文案改动后就失效了（429 的提示语已经换成
"这一分钟说得有点多…"，测试还在找"过于频繁"）。现在门禁是四条：selftest 27 / pytest 122 / vitest 50 / tsc。
